# Cypress Automation Portfolio

![Cypress](https://img.shields.io/badge/Cypress-13.17-17202C?logo=cypress&logoColor=white)

End-to-end UI test automation framework built with **Cypress**, targeting a public demo e-commerce site ([automationexercise.com](https://automationexercise.com)), structured around the Page Object Model.

## Why this project

Since production code and business logic from my commercial QA work are covered by an NDA, this portfolio demonstrates the same automation skill set — Cypress, Page Object Model, maintainable test structure — on a public site, in the open.

## Tech Stack

- **Cypress** — E2E test execution
- **TypeScript** — statically typed test code, page objects, and configuration
- **Page Object Model (POM)** — selectors and page actions encapsulated in dedicated classes, separate from test specs
- **JavaScript (Mocha/Chai syntax)** — test assertion syntax (via Cypress, compiled from TypeScript)
- **GitHub Actions** — CI pipeline, tests run automatically on every push to `main` and on every pull request
- **Colocated test data (`data.ts`)** — each spec's input values and expected results live in a `dataProvider` object next to the spec, kept separate from test logic
- **Claude Code** — AI-assisted QA workflow with specialised subagents (see [below](#ai-assisted-qa-workflow-claude-code))

Each feature gets its own folder under `e2e/`, with the spec and its `data.ts` colocated. Page Objects live in a sibling `page_objects/` folder inside `e2e/`, grouped the same way — one folder per feature area, each holding its `*PageArea.ts` file (exporting a `*Area` class, e.g. `CartArea`, and a ready-to-use instance) and a sibling `mapping_*.ts` selectors file.

### Why Page Object Model

Each `*Area` class owns the actions and assertions for its page, while its sibling `mapping_*.ts` file holds only the selectors. Specs call chainable methods (e.g. `productsPage.searchProduct(term).verifyProductsDisplayed()`) and read like a sequence of business actions rather than raw DOM queries. If the site's markup changes, only the mapping file needs an update — no hunting through test files.

## Getting Started

```bash
# clone the repository
git clone https://github.com/OMushtyn/cypress-automation-portfolio.git
cd cypress-automation-portfolio

# install dependencies
npm install

# open Cypress Test Runner (interactive mode)
npm run cy:open

# run all tests headlessly
npm run cy:run

# run all tests headlessly in Chrome — same browser as CI
npm run cy:run:chrome
```

## CI/CD

Every push to `main` and every pull request trigger an automated test run via GitHub Actions; a run can also be started manually from the Actions tab. Failed runs upload screenshots as build artifacts for debugging.

### Notable CI consideration: browser locale

Some tests assert the exact text of native HTML5 validation messages (e.g. "Заповніть це поле."). These messages are generated by the browser itself and depend on its UI language — which differs between a local machine and a fresh CI runner. To keep results consistent, both an Ubuntu language pack and a pinned `--lang` flag in `cypress.config.ts` are used to force Chrome's UI language to `uk-UA` in every environment.

## AI-assisted QA workflow (Claude Code)

The repository includes a [Claude Code](https://code.claude.com/docs) setup that splits QA work between specialised AI subagents — from test planning to defect reports. Every decision that matters (approving a plan, accepting changes, committing) stays with a human.

### What's included

- **`CLAUDE.md`** — project conventions Claude follows in every session: structure, naming, selector and data rules, known specifics (such as the pinned Ukrainian locale)
- **`.claude/settings.json`** — permissions: what Claude may run without asking, what needs confirmation, what is forbidden
- **`.claude/agents/`** — five subagents, each with one role:

| Agent | Role | Can change files |
|---|---|---|
| `test-planner` | Feature test plan: scope, risks, test cases with test design techniques | Only `docs/test-plan.md` |
| `test-writer` | Automates approved test cases, applies review comments and fixes | Only `cypress/e2e/` |
| `test-reviewer` | Code review of tests against project conventions | No |
| `flaky-investigator` | Reruns failing tests and classifies the root cause | No |
| `bug-reporter` | Standard defect report for confirmed site defects | Only `docs/bug-reports.md` |

- **`.claude/commands/qa-cycle.md`** — the `/qa-cycle` command that runs the agents in order

### How the cycle works

```
test-planner → [human approves the plan] → test-writer → test-reviewer
                                               ↑               │
                                               └── changes ────┘
failing test → flaky-investigator → test issue  → test-writer
                                  → site defect → bug-reporter
```

Each agent ends its response with a Handoff block (status and next agent), so the route is explicit rather than improvised.

### Guardrails

- The plan is a draft until a human sets its status to `Approved`; tests are never written from a draft
- Reviewer and investigator are read-only
- `test-writer` must never weaken a test to make it pass: if the site behaves wrong, the case goes to investigation instead
- Loop limits between agents prevent endless back-and-forth
- CI workflows, secrets and `git push` are denied for Claude; commits are made by a human after reviewing the diff

### How to use

Requires [Claude Code](https://code.claude.com/docs) with an active Claude subscription or API key. From the repository root:

```bash
claude
```

Then, inside the session:

```
/qa-cycle Registration
```

Agents can also be called directly, e.g. `@agent-test-reviewer review cypress/e2e/CartCheckout/`.

### Status

The agents have been run on the existing suite:

- `test-reviewer` reviewed all specs and page objects and found three tests that could never fail (a guest checkout check that only verified the unchanged cart URL, a category filter check that passed without filtering, and a multiple-products check that counted rows without checking names)
- `test-writer` fixed them; each fix was verified by deliberately breaking the behaviour and confirming that the test fails
- `test-planner` produced the approved CartCheckout test plan in [`docs/test-plan.md`](docs/test-plan.md): 22 test cases with test design techniques and coverage status

The first site defect, BUG-001 (the cart accepts a negative quantity), was found by manual exploratory testing and is documented in [`docs/bug-reports.md`](docs/bug-reports.md) in the format used by `bug-reporter`.
